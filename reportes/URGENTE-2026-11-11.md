## U2 — Restablecimiento de contraseñas en bloque (backend)

### Reglas

- `clasificacion`: `ACTIVOS`, `PASIVOS` o `AMBOS` (condición de trabajador de
  `RepoCondicionTrabajador`). En `AMBOS` entran también las cuentas sin
  asignación.
- `alcance`: `SIN_PRIMER_INGRESO` (por defecto) = la clave vigente sigue siendo
  la cédula; `TODOS` = todas las cuentas activas.
- Se excluyen **siempre** las desactivadas y las administrativas; se omiten y se
  cuentan, no fallan.
- `motivo` obligatorio, 10–500 caracteres.
- La ejecución exige que `confirmacion` coincida con el número de la vista
  previa y toma un candado de caché de 2 h.
- Auditoría `identidad.acceso_restablecido_bloque` con actor, filtro, motivo,
  `enviar_correo` y totales.
- U2-bis: `SIN_PRIMER_INGRESO` **no rehashea**; solo renueva el vencimiento y
  limpia bloqueos (la clave ya es la cédula). `TODOS` mantiene el flujo completo
  de `restablecer_acceso`.

### U2-bis — vista previa asíncrona y barata

`RepoCuentasClaveInicialORM.con_clave_inicial()` tardaba >10 min con ~1000
cuentas por el `check_password` Argon2 de cada una. Ahora:

- `POST preview/` **encola** una tarea y responde **202** con `task_id`; el
  estado se consulta en el mismo endpoint de estado.
- La tarea de preview guarda en caché, **30 minutos y por actor + clasificación
  + alcance**, la **lista de `cuenta_id` elegidas**.
- La ejecución recibe esa lista y **no vuelve a comprobar hashes**;
  `confirmacion` debe ser `len(lista)`.
- La selección incluye **sin `check_password`** las cuentas con fila en
  `identidad_cuenta_password_inicial` (la fila se borra al cambiar la clave).
  Solo se comparan las activas **sin fila**, y se descartan hashes vacíos,
  inutilizables (`!...`) o de algoritmo desconocido (`identify_hasher`).
- En `SIN_PRIMER_INGRESO` no se llama a `establecer_password`: solo
  `repo_password_inicial.emitir(...)`, limpieza de bloqueos y, si
  `enviar_correo`, el evento `PASSWORD_CAMBIADA`. Las sesiones no se revocan.

## Contrato exacto de los endpoints (U2)

Base: `/api/v1/identidad/usuarios/restablecer-acceso-bloque`

**Autorización (las tres rutas):** sesión válida (cookie) + permiso
`configuracion.editar` + cédula igual a `settings.SUPERADMIN_CEDULA`
(superadministrador). Cualquier otra cuenta: **403**.

### 1. Vista previa (asíncrona)

`POST /api/v1/identidad/usuarios/restablecer-acceso-bloque/preview/`

Cuerpo JSON:

```json
{
  "clasificacion": "AMBOS",
  "alcance": "SIN_PRIMER_INGRESO",
  "enviar_correo": true,
  "motivo": "Claves vencidas del personal (mínimo 10 caracteres)"
}
```

`clasificacion` ∈ `ACTIVOS | PASIVOS | AMBOS` (por defecto `AMBOS`).
`alcance` ∈ `SIN_PRIMER_INGRESO | TODOS` (por defecto `SIN_PRIMER_INGRESO`).

`202 Accepted`:

```json
{
  "status": "success",
  "message": "Cálculo de la vista previa en curso.",
  "data": { "task_id": "6b1d…", "estado": "EN_PROCESO" }
}
```

Al terminar, `GET .../<task_id>/` devuelve el resultado de la vista previa y la
tarea deja la lista de cuentas en caché 30 minutos para la ejecución.

Errores: `400` (validación, con `data.errores`), `401`, `403`, `500`.

### 2. Ejecución

`POST /api/v1/identidad/usuarios/restablecer-acceso-bloque/`

Mismo cuerpo **más** `confirmacion` (entero):

```json
{
  "clasificacion": "AMBOS",
  "alcance": "SIN_PRIMER_INGRESO",
  "enviar_correo": false,
  "motivo": "Claves vencidas del personal",
  "confirmacion": 120
}
```

`202 Accepted`:

```json
{
  "status": "success",
  "message": "Restablecimiento en curso.",
  "data": { "task_id": "3f2c…", "estado": "EN_PROCESO" }
}
```

`409 Conflict` (sobre C-1: `{"status":"error","message":"…","data":null}`) si:
- no hay vista previa vigente en caché (o pasaron más de 30 minutos),
- `confirmacion` no coincide con `len(lista)`,
- ya hay una ejecución en curso.

`400` validación; `401`; `403`.

### 3. Estado (preview y ejecución)

`GET /api/v1/identidad/usuarios/restablecer-acceso-bloque/<task_id>/`

Resultado de la **vista previa**:

```json
{
  "status": "success",
  "message": "Operación exitosa.",
  "data": {
    "task_id": "6b1d…",
    "estado": "LISTO",
    "resultado": {
      "estado": "LISTO",
      "revisadas": 120,
      "activos": 80,
      "pasivos": 40,
      "total": 120,
      "omitidas_administrativas": 3,
      "restablecidas": 0,
      "errores": 0,
      "enviar_correo": true,
      "dry_run": true
    }
  }
}
```

`total` es lo que se escribe en `confirmacion`.

Resultado de la **ejecución**:

```json
{
  "status": "success",
  "message": "Operación exitosa.",
  "data": {
    "task_id": "3f2c…",
    "estado": "LISTO",
    "resultado": {
      "estado": "LISTO",
      "revisadas": 120,
      "activos": 0,
      "pasivos": 0,
      "total": 120,
      "omitidas_administrativas": 0,
      "restablecidas": 120,
      "errores": 0,
      "enviar_correo": false,
      "dry_run": false,
      "clasificacion": "AMBOS",
      "alcance": "SIN_PRIMER_INGRESO",
      "motivo": "Claves vencidas del personal",
      "dias_vigencia": 7
    }
  }
}
```

`estado` (nivel superior): `EN_PROCESO` (PENDING/STARTED/RETRY), `LISTO`,
`ERROR` (FAILURE), `CANCELADO` (REVOKED); si la tarea terminó con
`CONFLICTO`/`EN_CURSO`, se refleja ese valor. En `ERROR` se añade
`"mensaje": "No se pudo completar el restablecimiento. Revise la bitácora."`.

`resultado` solo aparece cuando la tarea terminó. Errores: `401`, `403`.
